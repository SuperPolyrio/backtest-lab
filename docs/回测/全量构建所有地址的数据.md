如果你说的“地址”是 **大量 market / token / slug**，那应该启动这几类进程：

**1. market discovery 进程**

负责从 PostgreSQL 扫市场：

```text
core.markets
core.market_status_snapshot
```

做的事情：

```text
发现新 market
同步 slug / title / token_id / outcome_label
判断 active / resolved / final
写入 market_token_metadata
初始化 market_block_close_sync_state
```

这个进程可以每 5-10 分钟跑一次。

**2. final market backfill 进程**

专门处理已经完结的 market。

逻辑：

```text
找 status=pending 且 lifecycle=resolved/final 的 market
从 orderfilled_fact 全量聚合
写 market_token_block_close
标记 status=complete
以后不再重复跑
```

这个可以多 worker 并发，比如：

```text
4-8 个 worker
每个 worker 一次处理一个 market
大 market 按 block range 分片处理
```

**3. active market incremental 进程**

专门处理还在交易的 market。

逻辑：

```text
读取 last_processed_block
取 safe_block = 当前链上最新 block - N
从 last_processed_block - overlap_blocks 开始重算
删除/覆盖这段缓存
重新 INSERT block close
更新 last_processed_block
```

建议：

```text
运行频率: 1-5 分钟一次
safe_block: 50-200 blocks
overlap_blocks: 500-2000 blocks
```

这样可以处理晚到数据、重组、ingest 延迟。

**4. monitor / repair 进程**

负责检查：

```text
失败 market
长时间没更新的 active market
raw OrderFilled 行数和 cache trade_count 是否对得上
异常 0/100 尖峰
内部地址过滤是否生效
```

发现问题后把对应 market 标记为：

```text
status = retry / failed / needs_rebuild
```

我建议最终启动方式是：

```text
metadata-discovery-worker
final-backfill-worker x 4
active-sync-worker
cache-monitor-worker
```

如果你说的“地址”真的是 **钱包地址**，那逻辑不同：不要给每个地址单独生成价格走势。应该先生成全市场的 `market_token_block_close`，然后地址回测时用地址成交记录去 join 这张价格表。价格曲线是 market/token 级别，不应该按 wallet address 重复缓存。
