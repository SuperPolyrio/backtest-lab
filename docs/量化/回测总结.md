# Polymarket OrderFilled-first 回测开发方案

## 核心判断

Polymarket 回测不能按传统股票/币圈 OHLCV 思路做。最重要的数据不是“某个时间点的 close price”，而是链上/索引后的真实成交流：`OrderFilled`、`block_number`、成交价格、size、side、maker/taker 可推断字段、market/outcome 元数据、结算事件和现金流。

我们的主线应该是：

1. `orderfilled_block_close` 负责构建 block 级价格轨迹。
2. `OrderFilled` 明细负责构建成交概率、流动性、方向、滑点和账本。
3. 回测订单不能默认成交，而必须进入执行模型：成交、部分成交、未成交、滑点成交、延迟成交。
4. 每次 run 必须可复现：参数、代码版本、数据版本、block range、gap report、source quality 都要落库。

历史 CLOB depth snapshot 可以作为增强输入，但不能作为全量依赖。Polymarket 市场/outcome 数量太大，全量采集和长期存储 L2 盘口不现实；没有历史 L2 时，应以 OrderFilled-first 模型为主。

## 分级原则

- P0：没有它，回测结论大概率是错的。
- P1：没有它，结果能跑但不能用于严肃判断。
- P2：提高解释力、产品化和批量研究能力。
- P3：锦上添花或未来 live/paper parity 需要。

## P0：必须先做对

### 1. Block 轴和数据源边界

**要求**

- `orderfilled_block_close` 必须以 `block_number` 为主轴。
- 不要把 block close 强行合并成 1m/timestamp K 线。
- frontend price、CLOB current price、OrderFilled block close 必须分开标识。

**原因**

OrderFilled 是链上成交事实，block 是真实排序单位。把它强行转成时间 K 线，会引入错位、插值和错误成交顺序。

**开发注意**

- API 入参需要显式带 `source=orderfilled_block_close`。
- chart 和 backtest 的 x-axis 必须支持 `block_number`。
- 回测报告里要记录 `first_block`、`last_block`、rows、gap。

### 2. OrderFilled-first 执行模型

**要求**

策略产生的是“订单意图”，不是“必然成交”。

每个订单必须经过执行模型：

- `FILLED`
- `PARTIAL_FILLED`
- `NO_FILL`
- `REJECTED`
- `CANCELED`
- `CANCEL_FAILED`

**执行输入**

- 当前 block 的成交量
- 当前 block 的成交笔数
- 价格跳动
- 方向/side
- market/outcome 活跃度
- 策略订单大小
- 延迟/滑点参数

**开发注意**

- 不允许 `signal -> close_price -> position` 直接成交。
- 未成交订单也必须落库，否则回测会系统性高估收益。
- 每个 signal 要有 lifecycle：`signal -> submitted -> execution_result -> ledger_event`。

### 3. 成交概率模型

**要求**

没有历史 L2 时，用 OrderFilled 的历史成交流估算 fill probability。

基础模型可以先做 deterministic/stress 两套：

- neutral：按 block volume、trade count、订单占比估算成交概率。
- conservative：默认 50% 成交率上限，叠加 1-2¢ 不利滑点。
- stress：薄流动性/尾盘/高波动时更低成交率、更高滑点。

**关键指标**

- `fill_probability`
- `expected_fill_size`
- `actual_fill_size`
- `expected_fill_notional`
- `actual_fill_notional`
- `block_volume`
- `trade_count`
- `participation_rate`
- `no_fill_reason`

**当前实现**

- 执行层已经把 `expected_fill_size / expected_fill_notional` 和 `actual_fill_size / actual_fill_notional` 分开输出：前者表示按历史 OrderFilled 流动性、cap 和 stress 参数推出来的可期待成交，后者表示本次模拟真正进入订单和账本的成交。
- `quant_backtest_orders` 订单生命周期行会保存 expected/actual 字段和 `participation_rate`，Fill Quality Report 会汇总总期望成交、总实际成交和平均参与率；run artifact audit 会把这些字段作为 fill quality 和 parity contract 的必填项。
- 这个合同的目的不是新增 LOB，而是让 fill-first 模型能解释“信号有了但没成交”“历史成交量够但 min-fill/延迟/滑点后没进入账本”“订单占历史流动性比例过高”这三类问题。

**开发注意**

- 不要把 block volume 当作自己一定能吃到的流动性。
- 订单大小越接近 block volume，成交概率应非线性下降。
- 价格快速跳动时，成交应偏向不利价格。

### 4. OrderFilled 去重与归因

**要求**

不能简单 sum `OrderFilled.volume`。Polymarket 的 maker/taker 双边记录可能导致成交量和现金流双算。

**必须处理**

- maker/taker 双边归因
- `txHash` 不能无脑去重，因为同一 tx 内可能有真实多笔成交
- YES/NO complement
- multi-outcome 同一事件下的归属关系

**开发注意**

- 建议先定义 canonical fill key：
  - `tx_hash`
  - `log_index`
  - `condition_id`
  - `token_id`
  - `maker/taker`
  - `side`
- volume 指标分成：
  - raw orderfilled volume
  - deduped matched notional
  - strategy available notional

### 5. 现金流账本，而不是价格差 PnL

**要求**

PnL 必须基于 cashflow ledger。

公式口径：

```text
Σ(SELL + REDEEM + MERGE + REBATE)
- Σ(BUY + SPLIT)
+ 持仓市值
```

**必须记录**

- shares delta
- cash delta
- fee
- rebate
- realized PnL
- unrealized PnL
- settlement/redeem
- residual position

**开发注意**

- `REWARD / REFERRAL / CONVERSION` 不计入策略交易 PnL。
- 回测交易表和账本表分开：trade 是成交事实，ledger 是资金事实。
- 多 outcome event 要能检查概率/仓位约束。

### 6. 净收益优先

**要求**

所有报告默认展示净收益，不以毛收益为主。

必须进入成本模型：

- fee
- maker rebate
- taker rebate
- Tier
- gas/redeem 成本
- 资金占用
- slippage cost

**开发注意**

- 页面可以展示 gross PnL，但排序和策略评估必须用 net PnL。
- 参数快照要记录 fee/rebate 模型版本。

### 7. 利用数据库键和预聚合表做快路径

**要求**

在线回测不能每次从 14 亿级 raw `orderfilled_fact` 里现场 group all markets。回测输入必须优先走按 key 可命中的预聚合表和限定范围查询。

**当前数据库特性**

- ClickHouse `orderfilled_fact` 排序键适合按 `market_id + token_id + block_number range` 读取：

```text
ORDER BY (market_id, token_id, block_number, log_index, tx_hash)
```

- Postgres `quant.market_token_block_close` 是 block 级回测主输入：

```text
PRIMARY KEY (token_id, block_number)
INDEX (market_slug, token_side, block_number)
INDEX (market_id, token_side, block_number)
```

**推荐在线回测路径**

1. 用 `market_slug`/`market_id` 精确定位 market 和 outcome token。
2. 用 `token_id + block_number range` 或 `market_id + token_side + block_number range` 读取 `market_token_block_close`。
3. Python 只处理已经过滤后的几千到几十万行 block 级数据。
4. 如果需要 OrderFilled 明细，只允许带上 `market_id + token_id + block_number range` 去 ClickHouse 查，不允许全局扫描。
5. 策略报告和 UI 使用 run 结果表，不反复重算 raw facts。

**热门 market 预聚合**

热门 market/outcome 应提前构建或增量维护这些聚合：

- block close price
- block VWAP
- block volume
- trade count
- side bucket
- maker/taker stats
- raw/internal/invalid/anomaly counts
- gap/stale/source quality

**开发注意**

- 搜索、排行榜、全局 top-N、全局分位数不要放在线回测请求链路里。
- 模糊搜索如 `ILIKE '%nba%'` 只能用于异步/索引化搜索服务，不应用于回测数据读取。
- 每个查询都要先确认能命中排序键、主键或索引。
- 大范围统计要做 materialized summary，不要用户点击时临时扫全表。
- 如果 Python 慢，先检查 SQL 是否走对 key；不要第一反应改 C++/Rust。

## P1：决定回测是否可信

### 8. maker/taker 分开建模

**要求**

maker 和 taker 不能共用同一个 fill/slippage 模型。

**taker 重点**

- 立刻成交概率
- best ask/bid 拿不到
- 1-2¢ 不利滑点
- 延迟导致 stale price

**maker 重点**

- postOnly reject
- queue position
- adverse selection
- 好盘口不成交，坏盘口更容易成交
- fill 后 markout

**当前实现**

- `run artifact audit` 已新增 `Maker/Taker Execution Report`，从订单生命周期行里按 `maker` / `taker` 单独统计 submitted、filled、partial、no-fill、rejected、requested/filled notional、fill rate、no-fill rate、fill probability、participation、slippage、fee、rebate、execution cost、order type、time-in-force 和 1 block markout。
- 报告会输出 `maker_taker_verdict`、`execution_scope`、`role_counts`、`role_summaries` 和 `missing_roles`。如果订单缺少显式 role，或者只有 maker / 只有 taker，会标为 `role_specific` / review，避免把单角色样本当成 maker+taker 都校准过的执行模型。
- 这一步不引入 LOB；它的目的只是让 OrderFilled-first 模型在没有历史盘口时，也能把 maker/taker 的成交质量、滑点和成本口径拆开审计。
- 在暂时排除 LOB 的前提下，已新增 `Maker Queue Uncertainty Report`。它不声称知道真实 queue position，而是把 maker fill 的 OrderFilled-only 风险显式标出来：缺队列证据、参与率过高、raw trade 太薄、postOnly reject、cancel race、负 markout，并输出 `queue_uncertainty_verdict`、`risk_orders`、`suggested_fill_haircut_pct`。这一步用于防止 maker 回测把“价格击穿过”误当成“我的挂单一定排到了”。

**开发注意**

- GTC 不是天然 maker，关键看 `postOnly` 和是否立即成交。
- market order 本质是可立即成交 limit order，也要走 limit/taker 模型。
- maker 策略必须输出 markout：fill 后 N block/N 秒价格变化。

### 9. No Fill 是一等事件

**要求**

回测报告必须记录没成交的订单。

**报告字段**

- signal count
- submitted order count
- filled count
- partial fill count
- no fill count
- no fill rate
- missed profit
- adverse fill count

**开发注意**

- 胜率只按成交单算会严重失真。
- 策略看对方向但没成交，应记作 missed opportunity，不是盈利。

### 10. 延迟模型

**要求**

延迟是策略变量，不是系统噪音。

至少支持参数：

- signal delay
- data delay
- order submit delay
- fill confirmation delay
- cancel delay

**默认保守口径**

- 普通行情：几百 ms 到 1s
- 波动行情：1-5s
- FAK/FOK/cancel：可按 2-3s 压力测试

**开发注意**

- block 级回测也要模拟延迟：延迟后可能已经进入下一个 block 或更差价格。
- report 里要写清楚 latency profile。

**当前实现**

- `run artifact audit` 已新增 `Latency Profile Report`，单独输出 `latency_verdict`、`latency_profile`、配置的 `latency_seconds` / `latency_blocks`、平均 submit/cancel latency、effective latency span、FAK/FOK 订单数、cancel-sensitive 订单数、final-minute/high-volatility 订单数、`stale_price_risk_count` 和 `risk_orders`。
- 报告会把零延迟、FAK/FOK/cancel 但没有 2-3s 或至少 1 block stress、高波动/final-minute 但没有保守 latency 的订单标成 review，避免回测默认使用过于乐观的 instant fill。
- Strategy Tester 的 Fill Quality 页已显示 `Latency profile`、`Latency mode`、`Configured latency`、`FAK/FOK latency`、`Cancel latency` 和 `Stale risk`，复制 JSON 时会带上完整 `latency_profile`。

### 11. 滑点按 regime 建模

**要求**

滑点不能只是固定百分比。

至少按以下维度分层：

- liquidity regime
- volatility regime
- time-to-expiry
- final-minute
- order size / block volume
- price level

**开发注意**

- 60-70¢ 追价在趋势中后期可能 EV 转负。
- 尾盘、薄盘口、价格快速跳动时应自动使用更保守滑点。

**当前实现**

- `run artifact audit` 已新增 `Slippage Regime Report`，按 liquidity、volatility、time-to-expiry、final-minute、order size 和 price level 分层统计滑点。
- 报告会输出 `slippage_regime_verdict`、配置的 `slippage_bps` / `adverse_slippage_cents`、平均 slippage cost/bps、`risk_order_count`、`risk_regime_count`、`regime_summaries` 和 `risk_orders`。
- 当前版本仍是 fill-first / OrderFilled-calibrated 审计，不引入 LOB；它的作用是标记 thin/high-vol/final-minute、大成交占比、60-70¢ 追价等场景中固定滑点过于乐观的问题，后续可用 shadow/live fill evidence 校准每个 regime 的滑点参数。
- Strategy Tester 的 Fill Quality 页已显示 `Slippage regime`、`Slip risk orders`、`Slip risk regimes` 和 `Avg slip bps`，复制 JSON 时会带上完整 `slippage_regime`。

### 12. 高胜率/尾盘策略单独风控

**要求**

0.99、尾盘、最后几秒策略不能只看 win rate。

必须展示：

- payoff distribution
- tail loss
- max single loss
- ruin risk
- consecutive loss stress
- position concentration

**当前实现**

- `run artifact audit` 已新增 `Tail Risk Report`，从已落库 closed trades 计算 win/loss rate、gross/net PnL、payoff distribution、最大单笔亏损、最大单笔盈利、loss tail ratio、gross profit buffer、连续亏损 streak、0.95+ 高价格成交样本数、position concentration、losses-to-ruin，以及 1/3/5/10 连续亏损压力测试。
- `Tail Risk Report` 的 `risk_verdict` 和 artifact 完整性分开：报告能完整生成时结构是 ready，但如果高胜率策略存在单笔尾部亏损可抹掉累计利润，会在 `risk_verdict` 标成 review。
- Strategy Tester 的 Fill Quality 面板已展示 `Tail risk`、`Max loss`、`Loss streak`、`High-price trades`、`Ruin losses`、`Max conc`、`Payoff p10`，避免只看 win rate 或净收益。

**开发注意**

- 99% 胜率可能仍然长期亏。
- 马丁策略不得作为默认策略模板。
- 尾盘策略要单独 regime，不要和普通市场混算。

### 13. 结算源和市场生命周期

**要求**

短周期市场尤其要记录 settlement/source。

字段：

- resolution source
- settlement rule
- priceToBeat source
- oracle / Chainlink / TWAP / official rule
- market closed/archived/refund
- invalid/cancelled/misconfigured

**当前实现**

- `run artifact audit` 已新增 `Market Lifecycle Report`，单独记录 `market_lifecycle_status`、`resolved_outcome`、`end_date`、`resolution_ts`、closed/archived/refunded/invalid/cancelled/misconfigured/resolved flags、settlement/refund ledger 数量；如果 SETTLEMENT 模式下已经有 settlement trade，但缺 resolved outcome、end date 或出现 invalid/refund/cancel/misconfigured，会把 `lifecycle_verdict` 标为 review。
- `Settlement Compatibility Report` 继续记录 `final_valuation_mode`、`settlement_value`、`resolution_source`、`settlement_rule`、`price_to_beat_source`、`oracle_source`，并嵌入 `market_lifecycle_report`。这个报告负责判断结算源、market lifecycle 和 ledger/payoff 是否能兼容；如果 settlement trades 缺 source 字段、缺 settlement ledger，或 lifecycle report 为 review，会把 `compatibility_verdict` 标为 review。
- Strategy Tester 的 Fill Quality 面板已显示 `Settlement verdict`、`Settlement src`、`PriceToBeat src`、`Lifecycle`，避免结算源、oracle 或退款市场被静默当作普通 PnL。

**开发注意**

- price source 错误会让策略“精致地错”。
- market 异常退款不能当普通亏损/盈利处理。

## P2：产品化和研究效率

### 14. 数据质量报告

**要求**

每次 run 生成 data quality。

字段：

- block range
- row count
- gap count
- max gap
- stale count
- source mix
- frontend/orderfilled/CLOB fallback 次数
- dedupe stats

**当前实现**

- `run artifact audit` 已新增 `Data Quality Report`，从 `actual_data_quality` 和 Fill Quality 的 raw replay 证据汇总 `block_range`、`row_count`、`gap_count`、`max_gap`、`stale_count`、`source_mix`、`fallback_count`、`dedupe_stats`、`duplicate_count`、`jump_count`、`span_coverage_pct`。
- 报告会单独输出 `quality_verdict`：基础结构完整时 report 是 ready，但如果出现 fallback、gap、stale、raw duplicate、非 ready data status 会标 review；如果 rows 为 0、warning level 为 BAD 或覆盖率低于 50%，会标 invalid。
- Strategy Tester 的 Data Quality 页已显示当前 run 的 `Verdict`、`Warning`、`Rows`、`Gap count`、`Max gap`、`Stale count`、`Fallback count`、`Duplicates`、`Coverage`，不再只显示 benchmark artifact。

**开发注意**

- source quality 不达标时，结果要标 `warning` 或 `invalid`。
- 不允许 fallback 静默发生。

### 15. 环境异常时间线

**要求**

平台异常和策略表现分开。

记录：

- Gamma 异常
- CLOB 维护
- orderbook/API 状态不一致
- service not ready
- cancel/order 状态冲突
- market misconfiguration

**开发注意**

- 先排环境，再调策略。
- run report 里要能解释某段表现异常是否来自平台。

**当前实现**

- `run artifact audit` 已新增 `Environment Incident Report`，把当前 run 窗口内的 `quant.platform_incidents` 和 Fill Quality 的 `environment_flags` / `order_anomaly_flags` 合成独立环境诊断。
- 报告会输出 `incident_verdict`、`incident_count`、`severe_incident_count`、severity/component 计数、运行时环境旗标、订单异常旗标、incident timeline 和 `review_reasons`。
- 没有 warning/error/critical incident 且没有 runtime flags 时报告为 ready；如果有 Gamma/CLOB/API/service/cancel/order 状态冲突等环境证据，会标 review，避免把平台问题误判为策略参数或 fill model 问题。
- Strategy Tester 的 Fill Quality 页已显示 `Env incidents`、`Env severity` 和 `Env reason`，复制 JSON 时会带上完整 `environment_incident`。

### 16. Regime 分桶报告

**要求**

不要用一个平均收益概括所有市场。

分桶：

- market category: sports/crypto/politics/weather
- time-to-expiry
- volatility
- liquidity
- maker/taker
- final-minute
- event/outcome count

**当前实现**

- `run artifact audit` 的 `Execution Regime Report` 已按 `market_category`、`time_to_expiry_bucket`、`volatility_bucket`、`liquidity_bucket`、maker/taker `role`、`final_minute`、`event_outcome_count_bucket`、`no_fill_reason` 拆分订单生命周期，统计 submitted、filled、partial、no-fill、rejected、requested/filled notional、fill rate。
- `final_minute` 可从显式 flag 或 `time_to_expiry_seconds <= 60` 推导；`event_outcome_count_bucket` 会把单 outcome、binary、小多 outcome、中多 outcome、大多 outcome 分开，避免把 2-outcome 市场和 60-outcome 事件混算。
- Strategy Tester 的 Regime 页已显示当前 run 的 execution regime report，不再只看 benchmark bucket artifact。

**开发注意**

- 5m、15m、体育盘、多 outcome 长周期市场应分开评估。
- 策略参数不能跨 regime 无脑复用。

### 17. 回测 run 可复现

**要求**

每次 run 都有完整 artifact。

必须保存：

- run id
- code commit
- strategy name/version
- parameter snapshot
- data version
- block range
- source quality
- gap report
- fee/slippage/fill model version

**开发注意**

- UI 里展示的每个结果都要能回放。
- 参数修改后必须生成新 run，不覆盖旧 run。

**当前实现**

- 新建 run 时 `quant_backtest_runs.meta` 会保存 `code_commit`、`code_dirty`、`code_source`、`strategy_name`、`strategy_version`、`artifact_schema_version`、`model_versions` 和完整 `parameter_snapshot`/`parameter_fingerprint`。
- `run artifact audit` 已新增 `Reproducibility Report`，统一检查 run id、code commit、strategy name/version、parameter snapshot、data version、block range、source quality、gap report、fill/fee/slippage model version 和 artifact manifest。
- Strategy Tester 会显示当前 run 的 `Repro` verdict、`Code commit`、`Strategy ver`、`Fill/Fee/Slip model ver`，并在 `Reproducibility Snapshot` 里给出 replay command 和当前 run payload。

核心页：

- Overview
- Fill Quality

**开发注意**

**当前实现**

### 20. dry-run/live parity

**要求**

**开发注意**

- 回测 engine 输出订单生命周期。
- live engine 也输出相同 lifecycle。
- 两边差异用于校准 fill probability、slippage 和 latency。

**当前实现**

- `run artifact audit` 已新增 `Execution/Ledger Parity Report`，检查回测订单生命周期字段、cashflow ledger 字段和未来 live/shadow 事件字段是否共享同一套 contract。
- 订单侧要求 `order_id`、`signal_x`、`submit_x`、`side`、`role`、`order_type`、`status`、requested/filled/unfilled、fill probability、latency 和 `execution_source`；ledger 侧要求 BUY/SELL/SETTLEMENT 等 cashflow event 拥有 shares/cash/fee/rebate/slippage/cost/position/cash_after。
- 报告会单独输出 `order_schema`、`ledger_schema`、`live_event_contract` 和 `live_evidence`。缺订单、缺 ledger、缺关键字段会标为 `missing`；没有真实 live/shadow 证据但 schema 完整时，不阻断回测，只标记 live evidence 仍需校准。
- `Ledger Cashflow Validation Report` 进一步检查数值口径：用 ledger 的 `cash_delta`、`realized_pnl`、`cash_after` 复算 `net_profit_ledger`，并和 trade 表的 `net_profit_trade` 对比输出 `ledger_diff`、`missing_trade_ledger_count`、`residual_position`。它回答“净收益是否真的能从 ledger 推导”，不同于 parity report 的字段合同检查。
- Strategy Tester 的 Fill Quality 面板已显示 `Parity`、`Cashflow`、`Trade net`、`Ledger net`、`Ledger diff`、`Missing ledger`、`Parity orders`、`Parity ledger` 和 `Live evidence`；Reproducibility Snapshot 也会显示 `Cashflow verdict` 和 `Ledger diff`，复制 JSON 时会带上完整 `ledger_cashflow_validation`。

### A. 事件驱动和历史重放是主流方向

**来源**

- `evan-kolberg/prediction-market-backtesting`: https://github.com/evan-kolberg/prediction-market-backtesting
- 用户提供的 X 摘要：@AlterEgo_eth 等关于 NautilusTrader 扩展、真实交易重放、事件 hook 的讨论。

**要点**

- 成熟预测市场回测更接近 event-driven replay，而不是普通 dataframe 上算一遍价格差。
- 市场开放、关闭、resolution、订单成交、资金变化都应该是事件。
- 策略不应该直接读未来完整 dataframe，而应该按历史顺序接收 market/trade/fill/settlement 事件。
- 多 market 组合回测需要 joint replay，保证事件时间顺序一致。

**对本项目的开发要求**

- 先在 Python 层实现统一事件流：`MarketEvent`、`PriceBlockEvent`、`SignalEvent`、`OrderEvent`、`FillEvent`、`LedgerEvent`、`SettlementEvent`。
- `market_token_block_close` 是 block 级价格事件来源；OrderFilled 明细/聚合是成交质量事件来源。
- 多 outcome/event 批量回测必须按 block 顺序合并事件，不允许每个 outcome 单独跑完后再简单相加。

**当前实现**

- 已新增 `quant.backtest.event_stream`，定义 `BacktestEvent` 以及 `MarketEvent`、`PriceBlockEvent`、`SignalEvent`、`OrderEvent`、`FillEvent`、`LedgerEvent`、`SettlementEvent` typed contract。
- `build_backtest_event_stream` 可以把 block price point、策略事件、订单生命周期、fill evidence、ledger cashflow 和 settlement/refund 类事件统一排序；排序键是 `x_value -> priority -> market/outcome/order/trade`，为后续 multi-outcome joint replay 做基础。
- `run artifact audit` 已新增 `Event Stream Contract Report`，展示 schema version、event count、type counts、x axis、是否有序和缺失 contract；Strategy Tester 的 Fill Quality 面板会显示 `Event stream`、`Event schema`、`Event count`。
- 当前实现已包含事件流 contract、`Joint Replay Plan Report`、`Joint Replay Execution Report`、持久化 `joint_event_stream` run、原生 `native_joint_event_stream` runner 和审计层：单 outcome run 会标记为 `single_outcome_only`，多 outcome 输入能证明全局排序、ORDER/FILL/LEDGER contract 后才标记为 `joint_replay_ready`；`build_joint_replay_execution_report` 会直接消费合并后的 typed event stream，按全局 `x_value` 顺序更新 cash、position、fill、ledger、max cash-at-risk 和 portfolio equity。API 已暴露 `/quant/backtest-joint-replay` 和 `/quant/backtest-joint-runs`，后端 `build_native_joint_threshold_outcomes` 可以在一个任务里按全局 block 顺序对多个 outcome 产生 BUY/SELL/SETTLEMENT、trade 和 ledger，不再要求先跑多个单 outcome run 再拼接。前端 Batch Top-N 会直接提交 `nativeJointRun: true`，生成一个可查询、可审计的 native joint run，写入现有 run/orders/trades/ledger/equity/metrics 表并显示 `Joint execution` verdict、joint run id、joint max risk 和 portfolio equity。下一步重点变成用真实 shadow/live fill evidence 校准 fill probability、no-fill、slippage、latency，而不是继续把 batch 当逐 outcome PnL 相加。

### B. 缓存和材料化聚合是性能核心

**来源**

- `evan-kolberg/prediction-market-backtesting` README 提到 Rust-native conversion、staged data loading、materialized caches、unified cache/local/archive/API message bus。
- 本项目现状：ClickHouse `orderfilled_fact` 超过 14 亿行，Postgres 已有 `market_token_block_close` block 级聚合。

**要点**

- 快的回测系统通常不是每次扫 raw 数据，而是提前转换、分阶段加载、缓存、材料化。
- Python/Rust/C++ 只是执行层选择；真正决定速度的是数据布局和读路径。

**对本项目的开发要求**

- 热门 market 必须提前维护 block close、VWAP、volume、trade count、maker/taker stats、side bucket。
- 用户点击回测时，只读聚合后的 block tape 和必要的明细窗口。
- 全局搜索、top-N、跨市场统计必须走 summary/materialized table 或离线任务。
- 回测 run 保存输入 snapshot/cache key，确保同一次 run 结果可复现。

**当前实现**

- `run artifact audit` 已新增 `Materialized Replay Cache Report`，独立检查 `source_table`、`access_path`、`data_version`、block/window、cache key、input snapshot 和 raw detail window。
- 报告会区分主价格输入是否来自 `quant.market_token_block_close`/block replay 这类材料化表，是否按 token/market + block range 命中 key，以及 raw `orderfilled_fact` 是否只是限定 market/token/window 的成交明细证据。
- Strategy Tester 的 Fill Quality / Reproducibility Snapshot 会显示 `Cache`、`Cache source`、`Cache access`、`Cache version`、`Raw detail` 和完整 `materialized_cache` JSON，避免以后把 raw scan 或缺 snapshot 的 run 当作正式结果。
- readiness 已把 `build_materialized_cache_report`、材料化表白名单、cache snapshot 字段和前端展示 token 纳入检查。
- 已新增 `quant.market_token_execution_summary` 和 `scripts/refresh_orderfilled_execution_summaries.py`，从 `market_token_block_close` 预聚合 token/outcome 级 `volume`、`trade_count`、`raw_trade_count`、maker/taker amount/share、raw/internal/invalid/extreme/anomaly counts、`side_bucket`、`liquidity_bucket`、block coverage。
- 已新增 `quant.market_execution_summary` 和 `quant.event_execution_summary`，从 token execution summary 继续汇总 market/event 级 liquidity、maker/taker、异常率和 bucket counts。
- 已新增 `/quant/execution-summaries`、`/quant/market-execution-summaries`、`/quant/event-execution-summaries` 只读 API，后续 top-N、研究筛选、跨 market/event 诊断可以读 summary 表，不需要在线 group block tape。
- benchmark universe selector 已优先读取 `market_execution_summary` 的 trade count、volume、block coverage 做候选排序和 coverage 判断，summary 缺失时再 fallback 到旧 metadata/progress。
- Quant 前端搜索默认会合并 `market_execution_summary`/`event_execution_summary` 候选，Strategy Tester 的 Market Screener 已新增 `Materialized execution summary` 排行，展示 market/event summary API 的 volume、trade count、token/market count、block range、maker share 和 liquidity bucket。
- `scripts/sync_orderfilled_block_close_from_clickhouse.py` 在写完 block-close rows 后会默认调用 `refresh_execution_summaries_for_tokens()`，只刷新受影响 token 对应的 token/market/event summary；需要排查或批量导入时可用 `--no-refresh-execution-summary` 临时关闭。

**仍需继续**

- 配置真实 order-state、wallet/cost、platform incident 和 external signal 外部源，让 review gate 从本地 fixture 进入长期生产采集。

### C. 执行建模必须显式包含摩擦

**来源**

- `evan-kolberg/prediction-market-backtesting` 文档索引包含 execution modeling：fees、maker rebates、slippage、passive orders/queue position、latency、limits。
- `distank/polymarket-backtest`: https://github.com/distank/polymarket-backtest，README 中明确写 spread、slippage、commission execution model。
- 用户提供的 X 摘要：ClawArbs、PolyBackTest/KalshiBacktest 等强调 top-of-book、size、orderbook fidelity、200ms latency、limit buffer。

**要点**

- 回测收益必须在摩擦后仍然成立。
- 预测市场的摩擦至少包括 spread、slippage、fee、rebate、latency、queue position、limit buffer、position limit。
- 没有历史 L2 时，也要用 OrderFilled 的成交量、成交笔数、价格跳动来近似 fill probability。

**对本项目的开发要求**

- 每个 strategy run 必须选择 execution profile：`optimistic`、`realistic`、`conservative`、`stress`。
- 默认报告展示 realistic/conservative，不允许默认只展示 optimistic。当前已新增 `Execution Profile Matrix Report`：benchmark 默认 profile bundle 包含 `fast:realistic` 和 `fast:conservative`，报告会输出 required/present/missing profiles、conservative 相对 realistic 的 PnL/fill-rate degradation，并在缺 conservative 时阻止 profile promotion；Strategy Tester Benchmark 已同步展示 matrix 摘要、profile rows 和 comparison degradation。
- 对每笔订单输出：`fill_probability`、`expected_fill_size`、`actual_fill_size`、`slippage_cost`、`latency_blocks`、`no_fill_reason`。
- maker/taker 必须分开统计，不允许统一成一个“成交价”。

### D. 专用指标不能只看 Sharpe/胜率

**来源**

- `evan-kolberg/prediction-market-backtesting` README 展示 cumulative Brier advantage、equity、P&L ticks、drawdown、Sharpe、cash/equity 等图表能力。
- AutoPredict/X 摘要强调 calibration、prediction accuracy、execution quality、drawdown、risk-adjusted return。

**要点**

- 预测市场策略有两个层面：预测是否比市场准，执行是否真的赚到钱。
- Brier score/Brier advantage 适合衡量“概率预测质量 vs 市场价格”。
- 只看 PnL 会把好运气、流动性、尾部暴露混在一起。

**对本项目的开发要求**

- Strategy Tester 增加 prediction quality 区域：
  - Brier score
  - Brier advantage vs market close
  - calibration bucket
  - realized outcome by predicted probability bucket
- execution quality 和 prediction quality 分开展示。
- 结果排序优先使用 net PnL + drawdown + fill quality；研究视角再看 Brier/calibration。

**当前实现**

- `run artifact audit` 已新增 `Prediction Quality Report`，从当前 run 的 closed/resolved trades 中提取预测概率、结算结果和 market close-line baseline，输出 `brier_score`、`market_brier_score`、`brier_advantage`、`calibration_buckets`、sample count 和 baseline fallback count。
- 报告把结构状态和可信判断分开：报告能生成时 `status=ready`；如果没有已结算样本，或缺少 market close-line baseline，只能用策略预测本身 fallback，会把 `prediction_verdict=review`，避免把“没有可比较基准”的 Brier advantage 当成有效结论。
- benchmark runner 和前端已有 `Prediction Quality` 区域；当前单 run 的 Prediction Quality 已进入 artifact audit、markdown 导出和 Strategy Tester 普通结果页。前端会优先显示当前 run 的 `prediction_quality_report`，没有当前 run artifact 时才 fallback 到 benchmark artifact。
- 当前已新增 `Performance Score Report`：单 run artifact 和 benchmark artifact 都会输出 `net_pnl`、`max_drawdown`、`sharpe`、`sortino`、`calmar`、`rolling_return`、`coverage_penalty`、`low_fill_penalty`、`brier_advantage` 和 `performance_score`。评分公式明确为 `net_pnl - max_drawdown - coverage_penalty - low_fill_penalty + 100*brier_advantage`，用于研究排序，不替代 Fill Quality 和 Prediction Quality。
- 前端 Strategy Tester 的 `Performance` 页已经展示 current run 与 benchmark 两个来源的 `Performance Score`，因此研究排序/晋级时能直接看到 requested run 的综合评分、ranking verdict、风险惩罚、覆盖惩罚和低 fill 惩罚。batch/split/walk-forward leaderboard 和参数稳健性排序也已优先使用 `performance_score`，没有评分时才回退到旧的 net PnL 口径。
- 参数搜索结果已新增 `Performance Score Validation Report`：它会检查 scored runs 顶部是否被低 `closed_trade_count/sample_count` 的小样本结果占据，并输出 `score_bias_verdict`、`top_small_sample_share_pct`、`small_sample_score_premium`、best small-sample 和 best reliable sample。这个 report 已进入 production parameter staging 门禁；只有 robustness、regime coverage 和 score bias gate 都为 ready，参数才允许进入 pending/approved staging。后续仍需要用真实长期样本继续校准 penalty 权重。

### E. 参数优化要防过拟合

**来源**

- `evan-kolberg/prediction-market-backtesting` README 提到 Optuna/TPE、samplers、multi-market runners。
- 用户提供的 X 摘要：避免只挑最佳单一参数，最好看参数组合平均表现；小样本/单 regime 会隐藏 edge 缺失。

**要点**

- 最优参数往往是历史噪声。
- 单市场、单时间段、单 regime 跑赢没有说服力。
- 参数优化要看稳定性，不是只看最高收益。

**对本项目的开发要求**

- 参数扫描报告必须展示：
  - best run
  - median run
  - worst decile
  - parameter sensitivity
  - regime split performance
- 默认禁止只把 best parameter 写成生产参数。
- walk-forward / train-test split 应进入 P2/P3 产品化路线。

**当前实现**

- 后端已新增 `Parameter Robustness Report`：从参数扫描、benchmark profiles、split/walk-forward rows 或导出的 run summary 中抽取 scored runs，统一输出 `best_run`、`median_run`、`worst_decile`、`parameter_sensitivity` 和 `regime_split_performance`。
- 报告明确区分“能生成报告”和“是否足够稳健”：`status=ready` 只表示报告结构可用；`robustness_verdict=ready/review` 才表示参数证据是否足够。单次 run、参数组合太少、缺少 train/test 或 walk-forward 证据时都会保持 `review`。
- 默认策略已经改成阻止 best-only promotion：`production_parameter_policy.default_action=do_not_promote_best_only`，只有跨参数、跨 regime 且有 train/test 或 walk-forward 证据时，才允许进入 `review_and_stage`。
- benchmark artifact 已保存 `parameter_robustness`，前端 Strategy Tester 的 Benchmark 页会展示状态、verdict、run 数、参数集合数、best/median/worst-decile、参数敏感性和禁止直接推广最佳参数的原因。

**仍未完全到位**

- 当前已新增 `quant.backtest.parameter_search_plan` 和 `scripts/plan_fill_first_parameter_search.py`，可以默认生成 `train/test/walk_forward` evidence mode，并强制包含 `realistic/conservative` execution profile 组合；输出的每个 plan item 都带 `parameter_fingerprint`、request payload 和进入 robustness rows 所需字段，默认 dry-run，不写库、不启动大规模回测。
- 当前已新增 `quant.backtest.parameter_search_results` 和 `scripts/check_fill_first_parameter_search_results.py`，可以把计划项和结果 rows 按 `parameter_fingerprint + evidence_mode` 对齐，输出 `coverage_pct`、缺失计划项、重复/计划外结果、required field coverage、`robustness_report`、`regime_coverage_report` 和 `production_parameter_staging`。这一步的意义是：参数搜索不是“挑一个最好结果”，而是先证明计划里的每个 train/test/walk-forward 组合都实际产出了可进入 robustness 和 regime coverage 的结果，再决定是否允许 staging。
- 当前已新增 `quant.backtest.parameter_search_runner` 和 `scripts/run_fill_first_parameter_search_batch.py`，可以直接消费 parameter search plan 批量执行。默认是 dry-run，只展示 planned payload；只有显式 `--execute` 才创建真实 backtest run，只有同时指定 `--stage-parameters --write-staging` 才会把 ready 的结果写入 `quant.production_parameter_staging`。runner 会把每次执行归一化成 robustness rows，再统一交给 `parameter_search_results` 和 staging gate 判断。
- 当前已新增 DB-backed 参数搜索调度层：`quant.parameter_search_batches`、`quant.parameter_search_batch_items`、`quant.backtest.parameter_search_scheduler`、`scripts/run_fill_first_parameter_search_scheduler.py` 和 API `/quant/parameter-search-batches`。它可以把 plan 持久化成 queued items，worker 显式 claim item 后执行，记录 `attempt_count/max_attempts`、`run_id`、`result_row`、失败错误、`retryable_count` 和 `canceled_count`，并输出 progress report 与 `parameter_search_results`。CLI/API 也支持 cancel batch 和 requeue failed/canceled/running items。這一步解决“大 universe 参数搜索中断后不能恢复、失败后不能重试、进度只能看终端输出、出错后只能手工 SQL 停止/重跑”的问题。

### F. Regime 覆盖比短期盈利更重要

**来源**

- 用户提供的 X 摘要：s1rozha_ 关于 60 天盈利样本不足、上线遇到未知 regime 即失效的讨论。
- 用户提供的 X 摘要：尾盘、BTC/ETH/SOL Up/Down、低波/高波、体育盘等实盘反馈。

**要点**

- 短期回测收益不能证明 edge。
- 策略必须在足够多失败场景里被测试过。
- 预测市场有很强的 regime 差异：crypto 5m、体育长周期、政治、天气、多 outcome event 都不是同一类问题。

**对本项目的开发要求**

- 每个 run 记录 market category、time-to-expiry、liquidity regime、volatility regime、final-minute 标记。
- 回测报告必须按 regime 分桶。
- 如果策略只在一个 regime 有效，UI 要明确标成 regime-specific，不要展示成通用策略。

**当前实现**

- 单次 run 的 `Execution Regime Report` 已负责订单生命周期分桶；本阶段新增 `Regime Coverage Report`，进一步判断覆盖范围是否足够支撑“通用策略”声明。
- `Regime Coverage Report` 会按 `market_category`、`time_to_expiry_bucket`、`liquidity_bucket`、`volatility_bucket`、`final_minute`、`event_outcome_count_bucket` 汇总样本、fill rate、win rate 和 PnL，并输出 `coverage_verdict`、`strategy_scope`、`regime_specific`、`narrow_dimensions`。
- 如果核心维度只覆盖单一桶，例如只跑 sports、只跑 active liquidity、只跑一个 time-to-expiry 桶，报告会标记 `strategy_scope=regime_specific`，避免把单一市场环境的盈利展示成通用 edge。
- benchmark artifact 已新增 `regime_coverage`；Strategy Tester 的 Regime 页会同时展示当前 run 的 `Regime Coverage Verdict` 和 benchmark 的 `Benchmark Regime Coverage`。

**仍未完全到位**

- 参数扫描、walk-forward 和 production staging 已经强制绑定到 `regime_coverage_report.coverage_verdict` 与 `performance_score_validation_report.score_bias_verdict`：`parameter_search_results` 会同时计算 regime coverage 和 score bias，`production_parameter_staging.staging_allowed` 必须同时满足 robustness、regime coverage 和 score bias ready，审批时也会拒绝 `regime_coverage_verdict!=ready` 或 `score_bias_verdict!=ready` 的参数。
- 还需要扩展真实 universe，让同一策略能系统性覆盖 sports/crypto/politics/weather、短期/长周期、薄/厚流动性、多 outcome 等组合，而不是依赖手动选择。

### G. 从 backtest 到 shadow/live 的闭环

**来源**

- `braedonsaunders/homerun`: https://github.com/braedonsaunders/homerun，README 强调 validate、backtest、enable、shadow/live 以及 backtest/shadow/live PnL triangulation。
- `slotpoly.com` 和用户提供的 X 摘要：simulation first。
- `PolyQuantLab` X 摘要：区分 backtest 和公开事前 audit。

**要点**

- 回测只是第一层，shadow/paper/live 才能暴露 fill model 是否失真。
- 同一策略需要比较 backtest PnL、shadow PnL、live PnL。
- 公开事前信号/audit 和事后回测要区分，不能混为策略有效证明。

**对本项目的开发要求**

- 回测、paper、live 共用同一套 order lifecycle 和 ledger schema。
- shadow mode 的未成交、滑点、延迟用于反向校准 backtest fill model。
- UI 需要展示 backtest vs shadow vs live 差异，差异大时优先怀疑 fill model。

**当前已经落地**

- 新增 `quant.backtest.shadow_live_triangulation`，把 `quant_backtest_calibration_orders` 的模拟/真实成交误差、`quant_backtest_cost_calibration` 的真实成本误差、真实订单状态事件数量和外部源状态合成一个 `Shadow/Live Triangulation Report`。

- Strategy Tester 的 Fill Quality 面板已展示 `Shadow/live` verdict、`Fill suspect`、shadow 样本数、成本样本数、真实状态事件数和 drift summary，避免只看 backtest PnL。
- 新增 `quant.backtest.promotion_gate`，run artifact audit 已输出 `promotion_gate_report`、`production_promotion_allowed`、`paper_promotion_allowed` 和 `allowed_next_modes`。`fill_model_suspect=true`、缺 shadow/live triangulation、数据质量/repro/cache/settlement 不 ready 时，不允许推进到 paper/live；regime-specific 策略可进入 paper review，但不能直接 live。

## 技术选型与校准协议

### 1. NautilusTrader 可以用，但不要把它当第一层真相

**结论**

NautilusTrader 可以作为专业事件驱动回测/执行框架使用，尤其适合：

- 多 market / 多 outcome joint replay
- order lifecycle
- portfolio/accounting
- strategy runner
- live/sandbox/backtest 统一接口
- 未来接更专业的 execution adapter

但是对本项目来说，NautilusTrader 不应该替代我们的 Polymarket 数据语义层。我们的第一层真相仍然是：

- `OrderFilled`
- `block_number`
- token/outcome/condition/event 关系
- settlement/redeem/split/merge/rebate cashflow
- maker/taker 和成交质量

**开发策略**

- 短期：继续以 root `quant/` 的 Python/SQL 引擎为主，把 Polymarket 语义和账本做准。
- 中期：把订单、成交、账本、事件流抽象成稳定接口。
- 长期：如果需要多市场组合 replay、专业 order lifecycle、live/backtest 统一 runner，可以把 NautilusTrader 接成一个 backend adapter，而不是重写数据层。

**注意**

不要为了使用 NautilusTrader，把 Polymarket 简化成股票/币圈 candle feed。Nautilus 只能承载事件驱动框架，不能替我们解决 OrderFilled 去重、NO_FILL、settlement、rebate、YES/NO complement 等语义问题。

### 2. Rust 可以用于性能内核，但现在不是主开发语言

**结论**

现在没有必要用 Rust/C++ 重写整个回测系统。当前最重要的是模型正确性，而不是裸算力。

**当前推荐**

- SQL/ClickHouse：负责 14 亿级 OrderFilled 的筛选、聚合、block window。
- Postgres：负责 quant 聚合表、run artifact、结果表、UI 查询。
- Python：负责执行模型、成交概率、账本、策略、报告。
- Rust：未来只用于热点内核，例如大规模事件 replay、fill simulation、参数扫描加速。

**什么时候需要 Rust**

- 单次回测要 replay 1000 万以上事件。
- 全市场批量参数扫描成为常态。
- order-level queue simulation 明确成为瓶颈。
- Python profiling 证明瓶颈在执行内核，而不是 SQL/IO/数据布局。
- 规则已经稳定，不需要频繁改业务语义。

**注意**

Rust 应该是局部加速层，不是业务逻辑第一落点。过早 Rust 化会拖慢 OrderFilled 模型、账本、数据质量、校准协议的迭代。

### 3. 原始数据口径

**回测主输入**

1. `quant.market_token_block_close`
   - block 级价格轨迹
   - close price / VWAP
   - volume
   - trade count
   - raw/internal/invalid/anomaly counts
   - block range / source quality

2. ClickHouse `orderfilled_fact`
   - 只在需要明细时读取
   - 必须限定 `market_id + token_id + block_number range`
   - 用于成交质量、side bucket、maker/taker、价格跳动、明细校验

3. 账本/非交易现金流
   - BUY / SELL
   - SPLIT / MERGE / REDEEM
   - MAKER_REBATE / fee
   - refund / invalid / archive 事件

4. market metadata
   - event/outcome/condition/token 映射
   - market status
   - end time
   - resolution source/rule
   - category/regime

**禁止**

- 不允许在线回测从全量 `orderfilled_fact` 做跨市场 group。
- 不允许只用 frontend price 当成交事实。
- 不允许没有 block range/source quality 的结果进入正式报告。

### 4. 成交模拟怎么做

策略产生的是 order intent，执行模型输出 fill result。

当前代码已经把这条边界落到 `quant/backtest/strategy_intents.py`：`StrategySignal` 保存策略名、版本、signal index、signal block/x、signal price 和 reason；`StrategyOrderIntent` 保存 side、limit price、size、submit_x、time-in-force、role、order type、liquidity cap、fee/rebate 和 execution model。builtin limit replay 不再直接在 engine 里构造 replay order，而是先用 `build_threshold_limit_intent()` 生成策略层意图，再通过 `to_replay_order_intent()` 交给 OrderFilled replay。订单 `meta.strategy_intent` 会保留这份结构，方便后续 shadow/live、校准和报告追踪每笔成交来自哪个策略 signal。

**订单意图字段**

- side: BUY / SELL
- role: maker / taker / auto
- order type: limit / market-like limit / postOnly / FOK / FAK
- target price
- size
- submit block
- latency profile
- max slippage

**成交模型输入**

- 当前 block close / VWAP
- 当前 block volume
- 当前 block trade count
- 最近 N block volume/trade count
- price jump
- volatility regime
- liquidity regime
- time-to-expiry
- side bucket
- maker/taker historical fill quality

**输出字段**

- `FILLED`
- `PARTIAL_FILLED`
- `NO_FILL`
- `REJECTED`
- `CANCELED`
- `CANCEL_FAILED`
- actual fill price
- actual fill size
- fill probability
- slippage cost
- latency blocks
- no fill reason
- markout after N blocks

**基础规则**

- taker：按真实 block 成交流估算可吃到的量；价格向不利方向滑动。
- maker：默认不假设好价格一定成交；要考虑 queue/adverse selection。
- postOnly：如果按当时价格会立即成交，应模拟 reject 或转为 taker，取决于策略参数。
- FOK/FAK：成交失败概率高于普通限价单，并受 latency 影响。
- 没有历史 L2 时，不能声称是 orderbook-accurate，只能是 OrderFilled-calibrated execution model。

### 5. 摩擦、滑点和成本

**必须进入模型**

- spread proxy
- adverse slippage
- fee
- maker rebate
- taker rebate
- position limit
- liquidity cap
- latency
- stale price
- cancel race
- gas / redeem / settlement 成本

**默认 profile**

- `optimistic`: 用于上界，不作为默认展示。
- `realistic`: 默认报告主口径。
- `conservative`: 用于判断策略是否仍能活。
- `stress`: 用于尾盘、高波动、薄流动性、0.99 策略。

**建议默认压力**

- 成交率上限可从 50% 起步校准。
- taker 不利滑点可从 1-2¢ 起步校准。
- 波动行情 latency 可从 1-5s 起步校准。
- maker fill 后必须看 markout，防止“坏单更容易成交”的幻觉。

### 6. 如何验证回测框架准不准

你后续提出的验证方式是正确的：**在 live 市场中，同一时刻让回测/模拟系统生成一笔订单，同时在 Polymarket 真实市场下同方向、同大小或可比大小的一笔订单，然后比较两者成交、价格、PnL 和仓位。**

这应该正式做成 calibration protocol。

**验证流程**

1. 选择 live market/outcome。
2. 固定策略参数、execution profile、order size。
3. 在同一观察时刻生成 shadow/backtest order intent。
4. 同时发送真实 Polymarket 订单。
5. 记录真实订单的：
   - submit timestamp
   - observed block
   - order id
   - requested price
   - requested size
   - actual fill price
   - actual fill size
   - partial/no fill
   - fee/rebate
   - position delta
   - cash delta
6. 在回测/模拟系统中用同一 order intent 生成 simulated fill。
7. 比较两边差异。

**核心误差指标**

- fill status error: 模拟成交但真实未成交，或真实成交但模拟未成交。
- price error: `abs(sim_fill_price - live_fill_price)`。
- size error: `abs(sim_fill_size - live_fill_size)`。
- slippage error: 模拟滑点和真实滑点差。
- position error: simulated shares vs live shares。
- cash error: simulated cash delta vs live cash delta。
- PnL error: 后续 N block / N minute / market settlement 的 PnL 差。
- latency error: simulated latency vs live observed latency。

**判定标准**

- 如果成交状态经常错，说明 fill probability 模型不准。
- 如果成交状态对但价格偏差大，说明 slippage/spread/latency 模型不准。
- 如果价格和成交量对但 PnL 错，说明 fee/rebate/ledger/settlement 模型不准。
- 如果短期对、跨 regime 错，说明 regime 分类和参数校准不足。

**校准闭环**

- 每一笔 live-vs-sim 对照都落入 `quant_backtest_calibration_orders`。
- 每日/每周生成 calibration report。
- 按 market category、time-to-expiry、liquidity、volatility、maker/taker 分桶统计误差。
- 用真实误差回写 execution profile 参数。
- 如果 live/backtest 差异超过阈值，UI 必须标记该策略/market 的回测可信度下降。

同一个 audit 还会输出 `Execution Regime Report`：按 market category、time-to-expiry bucket、volatility bucket、liquidity bucket、maker/taker role、final-minute、event/outcome count、no-fill reason 拆分订单生命周期样本，统计每个桶里的 submitted、filled、no-fill、partial、fill rate、requested/filled notional 和平均滑点。这个报告不是新撮合模型，而是防止把一个只在单一 regime 有效的策略误判成通用策略。API 已暴露 `/quant/backtest-runs/<run_id>/artifact-audit`，前端 Strategy Tester 的 Fill Quality/Regime 页面会显示 run credibility 和 regime report。

同一个 audit 还会输出 `Reproducibility Report`：它把 code commit、dirty 状态、strategy name/version、parameter fingerprint、data version、block range、source quality、gap report、fill/fee/slippage model version 和 artifact manifest 汇总成 `ready/review/missing` 结论。旧 run 缺 provenance 会被标成 missing/review；新 run 会在创建时写入这些字段，前端 Strategy Tester 的 Fill Quality 和 Reproducibility Snapshot 会直接展示。

同一个 audit 还会输出 `Execution/Ledger Parity Report`：它检查 backtest 订单生命周期、cashflow ledger 和未来 live/shadow 订单事件是否遵循同一套字段 contract。这个报告不引入 LOB，也不改变 fill-first 主线；它的作用是保证后续 paper/live 真实订单可以和回测订单逐字段对齐，用差异去校准 fill probability、slippage 和 latency。

同一个 audit 还会输出 `Event-Level Risk Report`：它把多 outcome event 的 outcome snapshot、订单、交易和 ledger 汇总到事件级，检查概率和、YES/NO complement、outcome correlation、每个 outcome 的 cash-at-risk 和 portfolio-level exposure。只有单 outcome 或缺 correlation 时会进入 review，避免 FIFA 这类多 outcome 市场只看单线 PnL。

如果旧 run 是早期版本生成的，缺少 `fill_quality` 或 fill metrics，可以用已落库的 `quant.quant_backtest_orders` 和 `actual_data_quality` 重建，不改订单事实和价格事实：

```bash
conda run -n polyBacktest python scripts/audit_backtest_run_artifacts.py \
  --run-id <run_id> \
  --repair-fill-quality \
  --format markdown
```

**最终目标**

不是让每一笔模拟都和真实完全一致，而是让误差可测、可解释、可校准。回测框架准不准，最终不由理论决定，而由 `backtest/shadow/live` 三方误差长期统计决定。

## 推荐开发顺序

### Phase 1：把回测从“价格回测”改成“执行回测”

1. 固定回测数据快路径：`market/token/block range -> market_token_block_close -> Python execution model`。
2. 确认所有在线查询都命中 `token_id/block_number`、`market_slug/token_side/block_number` 或 `market_id/token_side/block_number`。
3. 引入 order lifecycle 表/结构。
4. 记录 signal、submitted、filled、partial、no_fill。
5. OrderFilled block volume/trade count 驱动 fill probability。
6. 未成交订单进入报告。

### Phase 2：现金流账本

1. 新增 backtest ledger/cashflow 表。
2. BUY/SELL/REDEEM/MERGE/SPLIT/REBATE 分类型记录。当前已支持 BUY、SELL、SETTLEMENT，并新增 `GAS_COST`、`SETTLEMENT_COST`、`REDEEM_COST`、`CAPITAL_COST`，用于把 gas/redeem/settlement/资金占用成本纳入净收益。
3. 净收益从 ledger 计算，不再只从 trade price 差计算。当前 `net_profit` 已优先使用 ledger realized PnL，并且 run artifact 会输出 `Ledger Cashflow Validation Report`，量化 `net_profit_trade`、`net_profit_ledger`、`ledger_diff` 和缺 ledger 的 closed trades。

### Phase 3：maker/taker + slippage/latency stress

1. maker/taker 分模型。
2. latency profile 参数化。
3. slippage 按 liquidity/time-to-expiry/regime 分层。
4. fill 后 markout。

### Phase 4：报告和复现

1. run artifact 完整保存，当前 `Reproducibility Report` 已覆盖 code commit、strategy/model version、parameter snapshot、data version、block range、source/gap quality、artifact manifest 和 replay command；`Execution/Ledger Parity Report` 已覆盖订单 lifecycle、ledger cashflow、live/shadow event contract；`Event-Level Risk Report` 已覆盖多 outcome exposure、probability sum、YES/NO complement、correlation 和 cash-at-risk；`Market Lifecycle Report` 已覆盖 resolved outcome、end date 和异常生命周期 flags；`Performance Score Report` 已覆盖 Sharpe/Sortino/Calmar、rolling return、drawdown/fill/coverage penalty 和 Brier advantage 组件。
2. Data Quality report：每次 run 展示 block/window、row count、gap/max gap、stale、source mix、fallback、dedupe stats 和 ready/review/invalid verdict。
3. Fill Quality 页面替代单纯胜率页面；同时用 `scripts/export_backtest_fill_report.py` 支持按 run 导出独立 Fill Report，脱离前端查看 `no_fill_reason`、missed orders、raw evidence、真实订单状态和 calibration 缺口。
4. Regime report。
5. Tail Risk report：高胜率、0.99、尾盘策略必须展示 payoff distribution、最大单笔亏损、连续亏损压力、losses-to-ruin、仓位集中度和高价成交样本，不得只展示 win rate。
6. Market Lifecycle + Settlement Compatibility report：前者记录 resolved outcome、endDate、closed/refund/invalid/cancelled/misconfigured，后者记录结算源、settlement rule、priceToBeat/oracle source，并检查 ledger/payoff 是否匹配；异常生命周期不能静默进入普通 PnL。

### Phase 5：CLOB/live 校准

1. 对 watchlist/活跃策略市场采样 CLOB。
2. 比较真实 live fill 和 backtest fill。当前已有 `quant.quant_backtest_calibration_orders`、订单事件采集脚本、导入脚本、自动样本构造脚本、周期报告脚本、校准 API 和前端 trust 展示。
3. 回写校准参数。
4. 不尝试全量 L2 历史存储。

## 不要再踩的坑

1. 不要把 `orderfilled_block_close` 当普通 1m K 线。
2. 不要默认策略订单按 close price 成交。
3. 不要只记录成交单，忽略 No Fill。
4. 不要无脑 sum OrderFilled volume。
5. 不要用毛收益替代净收益。
6. 不要把 maker 和 taker 混成一个模型。
7. 不要忽略延迟、撤单和状态不一致。
8. 不要把平台异常当策略失效。
9. 不要用 win rate 判断尾盘/0.99 策略。
10. 不要把 CLOB 全量采集作为历史回测前提。
11. 不要在线回测时从 14 亿级 `orderfilled_fact` 现场 group all markets。
12. 不要在回测数据读取路径里使用全表模糊搜索或全局 top-N 统计。
13. 不要忽略数据库排序键、主键和索引设计；先让 SQL 走对 key，再考虑 Python/C++/Rust 优化。
14. 不要把 Python 慢简单归因于语言，很多慢查询其实是没有使用 ClickHouse/Postgres 的数据布局特性。
15. 不要只展示 optimistic 回测；默认至少展示 realistic/conservative。
16. 不要把最佳单一参数当成策略有效证明，要看 median、worst decile 和 regime split。
17. 不要只看 PnL/Sharpe，预测市场还要看 Brier、calibration 和 execution quality。
18. 不要把 backtest、shadow、live 混为一谈；三者差异大时优先怀疑 fill model。
19. 不要把外部信号源直接喂给策略，必须记录 observed_at、source、latency、payload hash。
20. 不要做跨市场/跨平台比较而不验证 resolution compatibility 和 timestamp alignment。

## 当前阶段补充：paper/live evidence gate

fill-first 主线暂时不依赖 LOB，但策略从 backtest 推进到 paper/live 时，不能只看回测 PnL 或单独的 promotion verdict。现在 run artifact 和前端 Strategy Tester 都会合成 `paper_live_evidence_gate`：

- `run_evidence_ready`：本次 run 的外部订单状态覆盖率和校准覆盖率都必须达到 100%。
- `missing_evidence_ready`：不能还有缺失的 order-state 或 calibration evidence。
- `promotion_ready`：fill-first promotion gate 允许进入 paper 或 live。
- `paper_allowed/live_allowed`：综合以上三类证据后的最终推进结论。

这一步的目的不是替代 shadow/live 校准，而是把“能不能推进到 paper/live”的判定从分散字段变成一个可审计结论。后续继续开发时，任何 paper/live runner、报告导出或前端按钮都应该优先读取这个 gate，而不是绕过它直接用 promotion gate 或 PnL 做判断。

本阶段已经把这个结论接入执行入口：`strategy_activation` 进入 paper/live 时必须同时通过 `promotion_gate_report` 和 `paper_live_evidence_gate_report`；`strategy_enable_state` 会保存 gate 状态并在启用时二次检查；`strategy_runner_guard` 即使读到 `enabled=true` 的旧行，也会再次要求 `paper_live_evidence_gate_report` 和对应模式的 `paper_live_*_allowed=true`；`guarded_executor` 生成 intent 时也会把 gate 快照写进 payload。这样后续真实 paper/live adapter 只能从已经通过 fill-first evidence gate 的 runner plan 继续往下走。

进一步地，`order_execution_adapter` 也不再只信任 `guarded_executor` 的输出。它在 dry-run 和真实 submit 前都会检查每个 intent 的 `paper_live_evidence_gate_report`、`paper_live_evidence_gate_status` 和当前模式对应的 `paper_live_paper_allowed/live_allowed`。如果 intent 是旧格式、手工构造、或 gate 不允许当前模式，adapter 会返回 `fill_first_gate_blocked`，不会调用外部 transport。外部 submit request body 也会携带 gate 快照，便于后续真实订单回执和 fill calibration 追溯。

生产启动前的 `fill_first_production_readiness` 也必须读取同一个 run artifact gate：在 `--check-db --run-id` 模式下，它会同时检查 run-level external evidence coverage 和 `paper_live_evidence_gate_report`，只有目标模式对应的 `paper_allowed/live_allowed` 为 true 时才允许 `launch_allowed=true`。`scripts/check_fill_first_production_readiness.py` 也支持 `--run-artifact-json`，用于 CI 或本地离线 preflight 验证 gate 传导；真实生产启动仍然应该使用 DB 里的 run artifact 和外部源 freshness。这样前端、runner、adapter、CLI 和生产 preflight 都使用同一个 fill-first 证据门禁结论。

## 最终目标

一个足够准且足够快的 Polymarket 回测系统，应该满足：

- 快：主路径基于 block 级 `orderfilled_block_close` 和聚合后的 OrderFilled 成交流，不依赖昂贵 L2 回放。
- 准：订单经过 fill probability、slippage、latency、fee/rebate、ledger，而不是 close price 必成交。
- 可解释：每笔收益能追到 signal、order、fill、cashflow、data source 和 market lifecycle。
- 可复现：每次 run 能用相同参数和数据版本重放。
- 可校准：未来 live/paper 的真实成交质量能反向校准回测模型。
